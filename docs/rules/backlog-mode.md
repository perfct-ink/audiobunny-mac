## Backlog Mode

Applies when the user says to work on the backlog or runs the `work` special command (see Special commands below), unless [prototyping-mode.md](prototyping-mode.md) is on, which replaces its merge and PR rules. It adds an autonomous, branch-per-task workflow on top of [backlog.md](backlog.md); where the two overlap, backlog.md's rules on task files still hold.

Don't stop to ask which task to take or to confirm scope. Work through the tasks in `docs/backlog/` one at a time, highest priority first (`p0` before `p1`, and so on), skipping tasks whose `depends_on` files are still in `docs/backlog/`. Before starting each task, check for `docs/backlog/.stop`; if it exists (the user creates it with `touch`), finish, commit and push the current task, then stop:

- **One branch per task, with a prefix.** Start each task from a fresh, up-to-date `origin/main` (fetch first) on a branch named `backlog/<task-filename-without-extension>`. Never stack one task's branch on another's (if a task truly depends on another, say so in its `depends_on` and leave it for after that merges), and never commit backlog work to `main`.
- **Push every backlog branch, started or finished.** Push each `backlog/*` branch (`git push -u origin <branch>`) right after creating it, before the first commit, and again after every commit, so the work is on `origin` whether the task ends complete, incomplete, blocked, unverified, or is cut short by `docs/backlog/.stop` or the end of the session. This push is pre-authorized in this mode and in prototyping mode, covers only `backlog/*` branches (merging a finished branch into `main` is a separate step, allowed only in prototyping mode), and doesn't deploy. Before you start another task or stop, the branch must be fully pushed (no local commits missing from `origin`) and its last commit must carry its final `Backlog-Status` trailer (see Branch completion status); pushes before that point need no trailer or progress note. If `origin/<branch>` already exists from an earlier session, check it out and continue on it instead of recreating it. If a push is rejected because `origin` has commits you don't have, fetch and rebase onto them; after rebasing your own branch onto a newer `origin/main`, push with `git push --force-with-lease`, never plain `--force`. If a push fails for any other reason (no network, no remote, no credentials), follow Branch completion status and carry on without asking.
- **Finish what you can.** Implement the task, add tests, update `docs/features/` and remove the task file in the same branch (see Completing Work in backlog.md), commit with a `git log`-style message, and push. Before every commit, and before moving on to the next task, run every check that can run in the environment: the full test suites (backend and web), linters, type checks, the build, and any migration or browser check the task touches. Fix failures before committing; never commit or move on with a known failure. If a check can't run here (no Docker, no `node_modules`, no network), try the nearest substitute that does (for example a syntax check), then say plainly in the commit message and your report which checks you couldn't run and what is therefore unverified. Unverified work is not a reason to stop: record what is needed to verify it (the missing tool, machine or account, and the exact commands to run) in that task's own file on its branch, under an `Unverified` section with `branch:` frontmatter, push the branch, and continue to the next backlog item.
- **On a blocker, push and note it.** If you hit something only the user can decide or do (a product or privacy call, a risky migration, new infrastructure, an account or secret), commit the work so far and push the branch. Record what's done and what's blocking in that task's own file on the same branch (a `Blocked` section, plus `branch:` frontmatter). Don't edit other tasks' files or any shared index. Then move to the next task.
- **Deliberately not building something is a valid outcome.** Keep the task file and write *why* in it (a migration risk, a product or privacy decision only the user can make, or a new-infrastructure call that "no new infrastructure without asking" in [conventions.md](conventions.md) covers), so the next session skips it on purpose instead of re-discovering the blocker.
- **Build the conservative version.** When a call is genuinely the user's, build the cautious option behind the blocker note rather than guessing silently, and document the choice in the feature doc.
- **Keep going until the user says to stop.** Backlog mode is a loop, not a single pass. After each task, immediately pick the next one and start it; don't pause to report, summarize, or ask whether to continue. Stop only for an explicit user stop request or `docs/backlog/.stop`. If every remaining task looks blocked or done, don't exit: re-fetch `origin/main` and the branch list (merges may have unblocked tasks), re-read each skipped task to see whether a conservative version can be built (see "Build the conservative version"), and use `docs/backlog/` follow-ups and the "Verify before trusting" checks below to find more work. Missing local tooling (no tests, no Docker, no network) is not a reason to stop: build what you can, commit it, and say plainly in the commit message and report which checks you couldn't run. Don't pause, announce, or ask before moving on to the next task: the user wants it done without a prompt, so finish one and start the next in the same turn. Keep any required progress updates brief and continue working in the same turn; never make an update a checkpoint that waits for a reply. Give the full per-branch report (complete, partial with blocker, or untested) only when the user asks for it or ends the session.
- **Pull requests (outside prototyping mode).** Pull request tooling may not be authenticated on every machine, so don't count on opening PRs from a session. Every pushed `backlog/*` branch must still end up with a PR: use the project's PR-opening command (see its docs) on a machine that is logged in to the right account, and write each branch's last commit message as the PR description. List every branch you pushed in your report so none are missed. If the project automates this (a CI workflow or make target that opens a PR per `backlog/*` branch), its docs say so.
- **Never merge or push to `main`, and never deploy, unless prototyping mode is on.** Otherwise the user reviews and merges. With prototyping mode on, merge a finished branch (one whose last commit has `Backlog-Status: complete` and whose checks pass) into `main` as a rebase merge (rebase it onto the latest `origin/main`, rerun the checks, then fast-forward `main`; no merge commits or squash merges, see Branches in [conventions.md](conventions.md)) and push `main`, following [prototyping-mode.md](prototyping-mode.md); push the branch itself first, and once main is pushed, delete the merged branch as prototyping-mode.md says (the one case where a `backlog/*` branch is meant to leave `origin`). Incomplete branches are never merged, in any mode. The one other exception is the `write` and `groom` commands pushing `docs/backlog/` edits (see Special commands).

### Branch completion status

Every backlog task uses a `backlog/<task-filename-without-extension>` branch, including in prototyping mode. Record readiness in the latest commit on that branch with exactly one Git trailer:

- `Backlog-Status: complete`: all acceptance criteria are met, required checks passed, feature documentation is updated, and the task file is removed. This means ready to merge; the task itself is finished only after merging.
- `Backlog-Status: incomplete`: work remains, a blocker exists, a check failed, or required verification could not run. Keep the task file on the branch, with `branch:` and `status: incomplete` frontmatter and a `Blocked` or `Unverified` section (or a progress section for other unfinished work) explaining what remains and how to resume.

Update the trailer whenever work changes readiness. Inspect it with `git log -1 --format=%B origin/backlog/<task-name>` after fetching; a missing or unknown status is incomplete until verified. A branch with no commits beyond `origin/main` (for example one pushed right after creation) has no status of its own: ignore any trailer on main's tip and treat it as incomplete. Check the code and checks before trusting a complete marker. Never merge an incomplete branch automatically. If saving progress is unsafe or a push fails, keep the local branch, name it as unpushed in your report (and, if the task file is still on the branch, in its `Blocked` section), retry the push at the next task boundary, and continue independent tasks without repeatedly asking the user. Do not bypass a known failing check to create a commit.

### Verify before trusting

Backlog and feature docs drift like any other doc. A "still unbuilt" note has turned out to be stale more than once because the fix had already shipped, and a checkmark can be wrong the other way. Check the code before believing either direction, and before deleting a task as already built.

### Special commands

There are four backlog commands. When the user's message is just "backlog", show this menu and wait for them to pick one:

- `write`: capture new backlog items.
- `groom`: refine the open backlog items.
- `list`: show the open backlog items in a table.
- `work`: work through the backlog.

"backlog <command>" (for example "backlog list") skips the menu and runs that command.

**Asking in `write` and `groom`.** Where the agent's interface offers clickable multiple-choice questions (a decision card or an ask-the-user tool with options), ask each question that way, with two to four options and the recommended one marked, rather than as plain text the user has to type an answer to.

Only `work` is backlog mode. `write`, `groom` and `list` are interactive: they don't use the autonomous loop, the `docs/backlog/.stop` check, or `backlog/*` branches, and they never implement a task.

- **`write`.** Interview the user about one new item at a time. For each, create a task file in `docs/backlog/` as described under Creating Backlog Items in [backlog.md](backlog.md) (kebab-case filename, objective, requirements, acceptance criteria). Then ask for the next item, and repeat until the user says they're done.
- **`groom`.** Go through the files in `docs/backlog/` one at a time, highest priority first. For each, ask the user about its gaps: unclear requirements, missing acceptance criteria, priority, dependencies, and whether to split or drop it. Update that task file with their answers before moving to the next one. Finish with one item before raising questions about another.
- **`list`.** Run `git fetch`, then print one table with a row per file in `docs/backlog/`. Columns: task (filename without extension), priority (`unset` if missing), `depends_on`, a one-line summary, and branch status. Take branch status from `origin/backlog/<task>`: its `Backlog-Status` trailer (see Branch completion status) and whether its copy of the task file has a `Blocked` or `Unverified` section (read it with `git show origin/backlog/<task>:docs/backlog/<file>`). Use `no branch` if the branch doesn't exist. This command changes nothing.
- **`work`.** Same as the user saying "work on the backlog": start the loop described above. Picking `work` is the go-ahead, so don't ask for confirmation.

**Saving `write` and `groom` edits.** When `write` or `groom` finishes (the user says they're done, or every item has been groomed), commit and push the changes straight to `main` without asking. This is an exception to "Never merge or push to `main`" above and to the "wait for the user to type commit" rule in [conventions.md](conventions.md), and it covers only changes under `docs/backlog/` made by these two commands. Fetch and rebase onto `origin/main` first, stage only `docs/backlog/` files, and use a `git log`-style commit message.
